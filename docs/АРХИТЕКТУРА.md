# Архитектура и обоснование: алгоритм vs ИИ

## Главный вопрос

> Можно ли решать задачу алгоритмически, или нужен ИИ?

Короткий ответ: **гибрид**. Не «чистый алгоритм» и не «ИИ переписывает документ».
Правильно распределить роли так, чтобы каждый инструмент делал то, в чём силён.

## Что на входе и выходе

**Вход:**
- Действующая Оферта (Приложение 7) — структурированный docx: нумерованные
  пункты (часть номеров — **автоматические**, не текст), 80+ сносок (реальные
  Word-footnotes с автонумерацией), приложения, таблицы.
- N документов «Изменения» — инструкции на естественном языке.

**Выход:**
1. Объединённый файл изменений — инструкции из всех документов, **в порядке
   следования пунктов Оферты**.
2. Текст Оферты с применёнными правками, **выделенными цветом** и/или как
   исправления Word.

## Почему не «чистый алгоритм»

Инструкции — свободный юридический текст. Даже в образцах формулировки плавают
(«дополнить», «изложить в следующей редакции», «после слов»), есть вложенные
кавычки-ёлочки, где разделитель фразы и кавычка совпадают в одном символе
(`«ООО СК «Сбербанк Страхование»`), новая редакция пункта живёт **отдельным
абзацем**, а номера пунктов вроде `2.44`/`1.2` в тексте Оферты —
**автоматические** (в document.xml их как текста нет). Regex справляется с
конкретными образцами, но ломается на первой новой формулировке — для
банковской Оферты это недопустимо.

## Почему не «ИИ переписывает документ»

Отдавать модели на переписывание юридический текст в сотни КБ нельзя: риск
галлюцинаций, тихой потери/искажения формулировок и разъезжания форматирования
неприемлем. Ошибка в тексте оферты — юридическое последствие.

## Решение: ИИ как парсер намерения + детерминированный движок

```
Документ «Изменения»
      │
      ▼
[ ИИ / OpenRouter ]  ── превращает свободный текст в СТРУКТУРНЫЙ JSON-список
      │                 операций { target, op, anchor, payload }
      ▼
[ Экран проверки ]   ── оператор подтверждает/правит распознанное
      │
      ▼
[ Детерминированный движок OOXML ]
      │   • находит цель (сноску по номеру/содержимому, абзац по началу редакции,
      │     таблицу приложения);
      │   • вставляет/заменяет ТОЛЬКО подтверждённый текст;
      │   • выделяет цветом (EE0000) или как исправление Word;
      │   • упорядочивает правки по позиции в Оферте.
      ▼
  Два docx на выходе
```

Ключевая мысль: **ИИ указывает координаты правки, текст Оферты меняет код**. Это
даёт гибкость к формулировкам и одновременно юридическую точность.

## Где точно нужен только детерминированный код

- Автонумерация сносок: «Сноска № 32» — это 32-я по счёту ссылка в теле, а не
  элемент с `w:id="32"`. Сопоставление и правка — строго кодом.
- Сохранение исходного docx байт-в-байт всюду, кроме точечных правок.
- Выделение цветом / режим исправлений, добавление строк в таблицу.
- Сортировка правок по структуре Оферты.

## Где ИИ даёт настоящую ценность

- Классификация типа правки и извлечение якоря/payload из свободного текста.
- Устойчивость к новым формулировкам, синонимам, опечаткам.
- Разрешение неоднозначностей (какой пункт/сноска имеется в виду) — с выносом
  спорного на подтверждение оператору.

## Роль человека

Оператор подтверждает распознанные операции перед применением. Это осознанный
контур контроля для юридически значимого документа, а не признак слабости
автоматизации.
